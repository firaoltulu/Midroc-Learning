# Frontend: phased prompts for Claude Code

The full spec is `claude-code-frontend-prompt.md`. Because it is long, run the build as a **sequence of shorter sessions**, one prompt per phase. Claude Code stays focused, each phase ends with something working, and you can review and commit in between.

## Before phase 1 (one-time setup)

1. Create the frontend repo and add:
   - `docs/SPEC.md` = the full `claude-code-frontend-prompt.md`
   - `reference/theme.ts`, `reference/brand/` (the four logo PNGs) and `reference/openapi.yaml` (generated by the backend)
2. Optional but recommended: copy the spec to `CLAUDE.md` in the repo root, so every session loads it automatically.
3. Start Claude Code in the repo and paste the **Standing rules** below at the start of each session (or put them at the top of `CLAUDE.md`).

## Standing rules (paste at the start of every phase)

```
You are building the frontend described in docs/SPEC.md (read it fully before
starting; reference/ holds theme.ts, brand/ and openapi.yaml, the source of truth
for the API). Work ONLY on the phase I give you. Follow the spec's architecture
(feature modules, boundaries), design rules, and i18n rules exactly; no
hard-coded UI strings; every string in both English and Amharic; use theme tokens,
never hex values. When the phase is done: run typecheck, lint, i18n:check,
check:deps and the tests; fix failures; commit with a clear message; then give me a
short summary (what you built, what differs from the spec or the backend contract,
open questions). Do NOT start the next phase. Ask before deviating from the spec.
```

## Phase 1: Project setup and boundaries

```
PHASE 1. Read SPEC sections 1 and 2. Scaffold the Vite + React + TypeScript
(strict) project with TanStack Router (file-based plugin, auto code-splitting),
TanStack Query, MUI, and the dev tooling listed in the spec. Create the folder
layout (app/, routes/, features/*, shared/*, locales/), the env validation
(zod), the Vite dev proxy for /api, and ESLint (jsx-a11y, i18next/no-literal-string),
Prettier, and dependency-cruiser rules that enforce the feature boundaries from
section 2. Add scripts: dev, build, preview, typecheck, lint, i18n:check (stub for
now), check:deps, gen:api, test, e2e. Add a placeholder home route.
Done when: build, typecheck, lint and check:deps pass, and check:deps fails on a
deliberate deep import (verify, then remove the test import).
```

## Phase 2: Theme, providers, app shell, brand

```
PHASE 2. Read SPEC sections 3 and 5 (app shell part). Install reference/theme.ts
into shared/theme (fix any compile issues; do not redesign it). Build the
providers (ThemeProvider with system/light/dark and a persisted choice, Query,
Router), the app shell (slim top bar, mobile drawer, skip link, route error
boundary, toast area, NotFound), the BrandLogo component (full | mark, light/dark
PNG chosen from the RESOLVED color scheme, stable API), the favicon from the mark,
and the shared UI components: StatusChip (status tokens), EmptyState, PageHeader,
ConfirmDialog, skeleton helpers. Add a temporary /design route that shows every
component in both themes.
Done when: both themes render correctly, focus rings and reduced motion work, and
a component test covers StatusChip tones in both schemes.
```

## Phase 3: Internationalization (English and Amharic)

```
PHASE 3. Read SPEC section 4. Set up i18next + react-i18next with typed keys,
namespaces per feature, language detection (saved -> browser -> English), <html
lang> and document.title updates, the LanguageSwitcher, and the font loading
(Inter always; Noto Sans Ethiopic dynamically ONLY for Amharic). Implement
formatDate/formatDateTime/formatRelative with the Ethiopian-calendar default for
Amharic, Gregorian for English, a user override, and a safe fallback. Implement
the real i18n:check (identical key sets, unused keys, placeholder mismatches) and
move all existing strings into locale files with complete natural Amharic.
Done when: i18n:check fails on a deliberately missing key (verify, then fix),
tests cover formatDate (both calendars + fallback) and the font being loaded only
for Amharic, and the /design route looks right in Amharic with long strings.
```

## Phase 4: Authentication and route guards

```
PHASE 4. Read SPEC section 5. Implement Firebase sign-in (email/password with
sign-up and reset, Google with popup-then-redirect fallback), email verification
flow, AuthProvider (loading | signedOut | signedIn), GET /me as the source of
truth for role and status, X-Token-Refresh handling, the _public / _authenticated
/ admin layout routes with beforeLoad guards (no redirect flash, ?redirect=
return path), suspended-account handling, sign-out clearing the query cache, and
the screens: login, signup, forgot password, verify email, account stub. Support
the Firebase Auth emulator through VITE_FIREBASE_EMULATOR.
Done when: guard tests cover loading, signed out, unverified, suspended and
non-admin cases, and I can sign in against the emulator.
```

## Phase 5: API client and data layer

```
PHASE 5. Read SPEC section 6 and reference/openapi.yaml. Run gen:api to create the
types. Build shared/api: the typed client (Bearer token per request, 401 refresh
and single retry, X-Token-Refresh, typed ApiError and NetworkError), the error
code -> translated message mapper (errors.* and validation.* namespaces, generic
fallback, issues[].path -> form fields helper), the query-key factories, and the
default Query options from the spec. Add MSW handlers and a test harness
(render with providers, signed-in/admin helpers).
Done when: tests cover 401 retry, token-refresh header, error mapping, and
unknown-code fallback.
```

## Phase 6: Catalog and course detail

```
PHASE 6. Read SPEC section 7 (catalog, course) and 3 (design rules). Build
/courses (debounced search, category from GET /courses/categories, language filter,
pagination, all in URL search params with zod validateSearch) and
/courses/$courseId (header, description at reading width, outline accordion with
item-type icons, the enroll / continue / edit / unenroll state machine, status
banners for owners). Include thumbnails with a branded fallback, skeletons, empty
and error states, and /learn (my enrollments with progress).
Done when: the enroll state machine and URL-driven filters are tested, and the
pages are checked at mobile width in both themes and both languages.
```

## Phase 7: Learning player (video and PDF)

```
PHASE 7. Read SPEC section 9 (shell, video, PDF). Build the player shell
(desktop side panel, mobile bottom drawer, previous/next, progress, completion
state) and the video item: YouTube IFrame API via youtube-nocookie, lazy-loaded,
resume from lastPositionSeconds, progress saved about every 15 s and on
pause/end/page hide (fetch keepalive), completion at >=90% or end, and the
"video unavailable" state. Build the PDF item: fetch as a blob with the auth
header, react-pdf (lazy), page navigation, zoom, download, an "Open" fallback for
poor inline support, completion on last page or "Mark as complete".
Done when: progress-saving and completion logic are unit tested, and the lazy
chunks do not appear in the catalog route bundle.
```

## Phase 8: Exam taking

```
PHASE 8. Read SPEC section 9 (exam). Build the exam flow: overview (instructions,
passing score, attempts left, time limit), one question at a time with a numbered
navigator, review step, confirmation for unanswered questions, a timer based on
expiresAt corrected for clock skew from the start response's Date header, polite
screen-reader announcements at set points only, auto-submit at zero, answers
persisted in sessionStorage per attempt and restored when start returns
resumed:true, the result screen (score, pass/fail with text, attempts remaining,
per-question results, correct choices only if returned), retry, and history.
Done when: tests cover the navigator, timer with skew, autosubmit, restore after
refresh, results with and without correctChoiceIds, and EXAM_TIME_EXCEEDED /
ATTEMPTS_EXHAUSTED handling.
```

## Phase 9: My courses and the editor for draft/rejected courses

```
PHASE 9. Read SPEC sections 7 (authoring) and 8 (draft and rejected). Build
/my-courses (list with StatusChip, rejection reason, pending-revision badge) and
the editor with Details, Content and Review tabs: debounced autosave with a
visible Saved/Saving/Error state, the module/item tree with dnd-kit drag and
keyboard reordering (calls the order endpoints with the full id list), the video
item (paste link, show verified title, map video errors to the item), the PDF item
(drag-and-drop, client checks, upload progress via XMLHttpRequest, attach
fileKey), the exam builder (settings and questions with client validation that
mirrors the backend), the Review tab (checklist, Submit for review, COURSE_INCOMPLETE
problems list), and the read-only state while pending_review.
Done when: tests cover autosave states, reorder payloads, exam validation, and
problem-list rendering; the tree is fully usable by keyboard.
```

## Phase 10: Editing a published course (working copy)

```
PHASE 10. Read SPEC section 8 (published courses) twice. Implement the zustand
working copy persisted per course in localStorage (keyed by a hash of the live
tree; stale drafts are discarded with a notice), loading from the pending
revision when one exists, ids preserved for existing items/modules/questions/
choices and NO ids for new ones, moved items keeping their id, field labels
("Applies right away" vs "Needs admin review" from one constant), immediate PATCH
for minor fields, the change-summary bar, Submit changes for review (PATCH major
fields, then PUT revision content), Withdraw, the unchanged result, PDF upload
now / attach on submit, video verification errors mapped to items, and the
STALE_REVISION and NOT_PUBLISHED handling.
Done when: tests prove ids are preserved, new items are sent without ids, minor vs
major routing is correct, and stale handling keeps the old working copy until
confirmed.
```

## Phase 11: Account and admin

```
PHASE 11. Read SPEC sections 7 (account) and 10. Build /account (language, theme,
date format override, sign out) and the admin area with dense layouts: dashboard
(metric cards, enrollment time-series chart with day/week/month and a range
picker, top courses; charts lazy-loaded), moderation (courses and revisions tabs,
course review page with the authoring view including exam answers, revision page
with from->to course changes, the content change list, proposed-tree preview,
approve/reject with required reasons, STALE_REVISION and ALREADY_DECIDED
handling), courses list and per-course analytics + enrollments (with remove), users
(search/filters, detail, role change, suspend/reactivate with confirmation,
SELF_CHANGE_FORBIDDEN and LAST_ADMIN messages, claimSynced note), and videos
(unavailable list, Run check now with summary).
Done when: tests cover the guard, the reject-reason requirement, role-change
errors, and the diff rendering; every table has filters in the URL, sticky headers,
empty and error states.
```

## Phase 12: Accessibility, performance, end-to-end tests

```
PHASE 12. Read SPEC sections 11 and 12. Run an accessibility pass (landmarks,
one h1 per page, label/error associations, aria-live, focus management on route
change and dialogs, lang on user content) with vitest-axe on key components and
Playwright + axe on key pages in both themes and both languages. Run a
performance pass: confirm code-splitting, report the catalog route's initial JS
(gzipped) against the ~200 KB budget and what's in it, lazy images with fixed
aspect ratios, no layout shift. Write the six Playwright flows from the spec
against a mocked API (page.route), with documented instructions for running
against the real backend and the Firebase Auth emulator.
Done when: axe reports no serious or critical violations on the tested pages, the
budget numbers are reported, and all e2e flows pass.
```

## Phase 13: Deployment and README

```
PHASE 13. Read SPEC section 13 and 14. Add the multi-stage Dockerfile (build, then
nginx), deploy/nginx.conf.example (SPA fallback, /api proxy on the same domain,
immutable hashed assets, no-cache index.html, compression, security headers with
a CSP starting point verified against real network traffic: YouTube nocookie
frames, Firebase/Google sign-in origins, same-origin API), and the README (setup,
env vars, Firebase project setup, emulator, gen:api, adding a feature module,
adding a translation key, the Amharic-review note). Then verify every item in the
Definition of Done (section 14) and report anything that does not pass.
```

## After phase 13

Ask Claude Code for a final audit prompt:

```
Audit the whole frontend against docs/SPEC.md section 14 (Definition of Done) and
the design/i18n/security rules. List every deviation with file and line, fix the
ones that are clearly bugs, and ask me about the rest.
```
